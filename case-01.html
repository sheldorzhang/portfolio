腾讯企点营销云 MAGIC AI

从功能驱动到意图驱动，设计 Agent-first 的产品体验方式

产品
腾讯企点营销云 MAGIC AI，面向企业增长的 AI Agent 营销平台
角色
负责 Agent 基础配置和任务协作体验（任务发起、执行过程、结果确认）；主导营销云 AI 设计体系建设及 AI-ready 工作流升级。
时间
2024 — 至今
关键词
AI Agent 体验 / Multi-Agent / Human-in-the-loop

01 产品与体验

MAGIC AI：把分散的营销能力组织成完整增长任务

企业已经有人群圈选、旅程编排、内容生成、企微触达这些营销工具，但做一场活动，仍要运营自己在多个模块之间把目标、人群和规则串起来。MAGIC AI 让运营直接提出增长目标，由 Agent 拆解步骤并调用这些工具执行。

下面用一场“秋冬换季沉默会员召回”活动演示完整流程。

MAGIC AI 把企业数据、营销经验和执行工具组织成可协作、可治理的智能增长系统。

Agent-first：从找功能，到提目标。

我负责的部分：运营直接接触的主路径，包括任务怎么发起、执行过程怎么展示、结果怎么确认和复用。下面的策略、组件和设计工作流都围绕这条路径展开。

02 发现与定义

问题：活动目标要靠运营自己在模块之间传递

产品转型的目标不是把每个功能都改成对话入口，而是让 Agent 接手跨模块的完整营销任务。所以我先要弄清楚：一场活动的目标、人群、规则和中途修改，现在是怎么在模块之间传递的。

跨角色协作：一场大促如何被接力完成

先看运营、算法、代理团队与知识库如何跨阶段协作，再看运营在页面间推进任务时遇到的断点。

体验旅程分析：同一个目标在哪些环节丢失

结合业务流程走查与行业交付反馈，沿运营视角梳理编排、执行、复盘阶段涉及的页面与回环。

发现有两点：

  • 营销能力都已经具备，但目标和人群条件要运营在每个模块重新录入。“同一组人群条件分别要在 CDP 中创建、在 MA 画布配置时搜索选中。”
  • 3 个角色需反复对接，知识策略都在本地：运营做策划、算法圈人群、代理做旅程配置。

设计机会：双向意图对齐

产品侧让用户从经营目标而不是功能入口发起任务；体验侧让 Agent 解释自己理解的目标与约束，允许用户在执行前补充、修正并确认。两者共同解决跨模块任务的上下文断点。

设计目标：Agent 先复述理解，人确认后再执行。 运营从经营目标发起任务；Agent 在执行前说明自己理解的目标、人群和约束，运营可以补充或修正。确认后的信息在后续每一步沿用，不需要重复录入。

03 体验策略

策略：按任务风险决定 AI 介入多深

并非所有营销任务都适合交给对话式 Agent。我用三个问题给任务分类：由谁发起？意图是否明确？出错代价多高？据此分出三种做法：

  • 每天都要看、但运营不会主动提问的信息 → 内嵌式 AI，放在工作台
  • 材料有歧义、需要人逐条判断的配置 → Copilot，AI 提取、人确认
  • 跨多个模块的长任务 → Multi-Agent，Agent 执行、人在关键节点确认

1. 洞察：把 AI 建议放进工作台首页

需求洞察

增长要持续判断哪些人群值得经营、上一场复盘能否复用。判断散落在多个模块，运营自行串联的门槛高。

我的做法

把 AI 建议放在运营每天打开的工作台首页，集中展示人群信号、复盘结论和建议动作。每条建议都附上判断依据，由运营决定是否执行。没有做成对话入口，是因为这类信息需要每天看，但运营很少会主动提问。

2. 规则配置：AI 提取，人逐条确认

需求洞察

交付时，前场同学要帮企业把活动规则文档整理成系统配置。规则文档里常有歧义和互相冲突的条款，让 AI 直接自动配置，出错代价太高。

我的做法

AI 负责从文档中提取规则，标出冲突条款和适用范围；运营逐条澄清、确认。只有确认过的规则才进入策略库，供之后的 Agent 任务调用。

3. 活动策划：Multi-Agent 执行，人在关键节点确认

需求洞察

真实任务里过程信息过多，活动分支也比演示更复杂。潜在诉求是中途可改，失败不必退出重做。

我的做法

主 Agent 维护整体目标，专业 Agent 分工处理。界面优先展示任务状态、关键产物和待确认事项，低价值过程默认折叠；条件变化或执行失败时，运营修改后可以从当前步骤继续。

04 基础体验

通用规则：三种模式共用一套交互

三种模式的用户都会问同样三个问题：Agent 能做什么？它打算怎么做？结果能不能直接用？我把这三个问题对应的交互统一下来，保证不同 Agent 用起来是一样的。

1. 发起任务：意图可见

用任务示例和输入引导告诉运营可以提什么目标，缺少人群、条件或约束时主动追问。

2. 理解与协作：过程可介入

关键计划、待确认动作和异常始终可见，其余步骤默认收起；运营可以修改或确认下一步。

关键决策：Agent 执行过程怎么展示

从 Markdown 全量平铺，转向按用户决策需求分层；再补充执行轨迹、任务进度与关键节点反馈。

3. 验收并执行：结果可用

结果可以核对和修改；运营确认后的规则和产物存入企业知识库，下次任务直接调用。

三类基础组件：Compose、Collaborate、Artifact

我把上面三条规则落成三类组件：Compose（任务输入与追问）、Collaborate（计划确认与过程反馈）、Artifact（结构化产物）。已接入 5 类 Agent，新 Agent 接入时不需要重新设计这几部分的交互。

05 验证与总结

验证意图驱动，沉淀可复用的体验能力

我从三个层面看效果：任务有没有完成、质量有没有守住、结果有没有出现。

1. 怎么验证

在产品设计侧维护问题方案清单，来源包括客户反馈、行为数据和竞品分析，每项跟进到上线和采纳。规则配置 Copilot、结构化产物都来自这份清单的记录与迭代。验证指标分三层：

  • 任务有没有完成：首次价值、重复使用、真实任务渗透。
  • 质量有没有守住：建议采纳、人工修改、规则纠错。
  • 结果有没有出现：触达转化、ROI、实验复盘。2026 年营销云产品线签约金额增速 +35%，已签约订阅制 KA 客户 160+ 家（产品线整体数据）。

2. 团队的 AI 设计工作流

产品、前端和设计都开始用 AI Coding 产出页面后，同一类页面出现了多种写法。我把组件规则、页面范式和使用方法整理成 AI 可读取的设计上下文与 Skill，用于页面生成和规范走查。设计师仍负责业务判断、设计取舍和规范维护，AI 按规范生成并检查。后来我用 Vibe Coding 把这套做法做成了个人工具 Be4D，详见《Vibe Coding 的设计品味与规则》。

3. 下一步：扩展到更多增长场景

这套协作方式在真实任务里形成了一个闭环：Agent 发现运营的潜在意图，交付可以直接使用的结果，效果反馈回到下一次任务，验证过的做法再扩展到新场景。接下来会把它用到更多增长场景，覆盖洞察、决策、执行和复盘四个环节。

我的体会

随着任务复杂度和模型能力提升，我认为 Agent 体验还有三件事要持续做：

  1. 确认交互：确认会从逐步确认变成按风险确认，低风险步骤交给 AI 推进，策略、人群、权益这类决策仍由人确认。
  2. 产出沉淀：用户确认过的产出要回到企业知识库，下次任务直接调用，Agent 才能越用越准。
  3. 过程信息：对话要贴合客户业务，展示用户在过程中需要判断的信息，不能过度收起、只给结论。

AI 生成效果和稳定性怎么判断，是我认为要长期解决的问题。
